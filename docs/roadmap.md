# Build roadmap

One box is roughly one day of work and one to three commits. The daily build job takes the
first unchecked step that is not marked **[needs you]**, builds it with tests, ticks the box
and pushes. Steps marked **[needs you]** require a GPU, a large dataset download, an account
or a judgment call, so the job skips them and leaves a note under "Waiting on you" instead.

Rules for every step: tests pass, lint passes, small conventional commits, and no invented
numbers anywhere. Benchmark results only appear when produced by `eval/` from a real run.

**Every commit must change the game for players** (project owner, 2026-10-16): it either adds a
layer players can use (a mode, a control, a screen, more photos) or fixes a problem players hit
while playing, proven by a test that fails without it. Roadmap edits, docs and refactors ride
along inside that commit; they never go in a commit of their own. The commit message says what a
player now sees or can do. Before picking a roadmap step, play a full game on a phone and a
desktop viewport (the Playwright suite) and fix what is broken first.

## Milestone 2.5 — Fresh games, a bigger world, visibly AI

Priority from the project owner (2026-10-13): a visit should never open on the same photos,
the catalog should grow to about 1,000 photos screened by AI rather than by eye, and the site
should show the model at work. These steps come before the rest of Milestone 3.

- [x] Web: every visit opens a fresh random five-photo game; the Daily Five moves behind a button, with tests for both modes
- [x] ML: AI scene gate, CLIP zero-shot screening for people, indoor scenes, text that gives away the place and non-photos, with thresholds checked against the 88 hand-reviewed photos and a small labelled reject fixture (`ml/src/whereabout_ml/scene_gate.py`)
- [x] ML: make the gate's indoor and not-a-photo reasons useful: the first calibration run (`data/scene_gate/report.md`) capped both thresholds at 1.0 because catalog photos scored near 1 (indoor: wm077; not-a-photo: wm126), so neither caught its labelled rejects. Cause: probability scores saturate near 1 and thresholds were rounded to three decimals. Scores and thresholds are now log-odds, and the report lists the catalog photos closest to each threshold for review (`data/scene_gate/README.md`); the `scene_gate.yml` run on push recalibrates and commits the new counts
- [x] Data: Commons harvester in CI: Quality and Featured images found by geosearch around GeoNames places in every 10° cell, grid-balanced, run through `ingest.py` (license capture, dedupe against the catalog) and the scene gate, place and country from the GeoNames gazetteer, pass/reject counts per reason (`ml/src/whereabout_ml/harvest.py`, `.github/workflows/harvest.yml`, output in `data/harvest/`)
- [x] Data: widen the harvest and grow the catalog from it: the first run (`data/harvest/report.md` at the time: 1,046 assessed files near 820 seeds, 307 harvested) showed discovery was the bottleneck, so the defaults are now 12 seeds and 30 candidates per cell, and seeds, candidates, per-cell cap, target and merge limit are workflow inputs. Its photos included many birds, insects and flowers, so the scene gate gained a `close_up` reason (nothing to locate) with its own fixture rows, calibrated, like every reason, on the hand-reviewed `wm` photos only. The harvest workflow now appends up to 150 harvested photos per run to `photos.csv` in grid-balancing order (`ml/src/whereabout_ml/merge_harvest.py`), rebuilds `photos.json` and starts the quality, labels and Atlas workflows; the Scene gate workflow starts the harvest when its thresholds change. - [x] Web: the site loads photos and Atlas's guesses in chunks so the bundle stays small: the home page ships only the playable ids and a content-hash version, the build writes one record per photo (`out/game-data/<version>/<id>.json`, from `web/src/app/game-data/[version]/[file]/route.ts`) and a game fetches the five it deals (`web/src/lib/game/deck.ts`); `npm run check-bundle` in CI fails if catalog data reaches the home page's scripts again

- [x] Web: "How Atlas works" gets an AI-curation section with the gate's real pass/reject counts and example rejects ("Choosing the photos", from `web/src/data/scene_gate.json`, rebuilt by `scene_gate.yml`)
- [x] Web: Pocket Atlas on the home page, "Try Atlas on your photo" (CLIP in the browser) as a first-screen card in the game header, one line on phones so the photo stays the hero

## Milestone 5 — Pocket Atlas catches up

"Try Atlas on your photo" runs ViT-B/32 in the browser and only zero-shot text matching, while
the game's Atlas has a heatmap, saliency, retrieval and trained heads. Each step brings one of
those to the photos players bring themselves, still entirely on their device, and any learned
part plays only if `eval/` shows it beats what Pocket Atlas does now on the catalog photos.

- [x] Web + ML: Pocket Atlas's heatmap: at the reveal of your own photo the globe shades every country by how sure Atlas was, as the game's reveal does, and says how sure it was of the country you pinned ("It gave Peru 36%", "under 1%" for one it all but ruled out, nothing over the sea) (`belief_from_probabilities` moves to `ml/src/whereabout_ml/belief.py` and is ported as `beliefFromProbabilities` in `web/src/lib/belief.ts`; `locate()` in `pocket_index.py` and `locate.ts` both return `belief` from the tempered probabilities, pinned by `data/fixtures/pocket_cases.json`; the pinned country comes from `countryAt`, the globe's own shapes)
- [x] Web: "Where Atlas looked" on your photo: occlusion saliency in the browser (a grid of grey patches, each one re-embedded, scored by how much the chosen country's probability drops), with the deletion-test faithfulness check ported from `saliency.py` and pinned to it by a shared fixture; shown as an overlay on the photo after the guess, behind a button so phones only pay for it on request (`web/src/lib/pocket/saliency.ts`, pinned to `saliency.py` by `data/fixtures/saliency_cases.json`, which also pins numpy's round-half-to-even cell edges; `deletion_drops` is split out of `deletion_test` so both sides can run on the same random cells; the encoder hands out CLIP's preprocessed pixels and embeds each greyed copy as a batch of one, because the 8-bit browser model quantises activations over the whole batch and batching changed every embedding; a run is dropped as soon as a new photo replaces it; the Atlas workflow's parity test asks where Atlas looked on the parity photo with the real model and records its deletion test in `pocket-parity.json`)
- [x] Fix: Pocket Atlas's parity test never passed (cosine 0.80 on the Atlas run of 2026-10-27), so the index was never published and "Try Atlas on your photo" stayed closed. Three causes, each measured against open_clip on test images in Chromium: the browser's 8-bit model (now `fp16`, about 180 MB), Python reading photos without their EXIF orientation while browsers turn them upright (`load_rgb` in `clip_encoder.py`), and open_clip running OpenAI's weights with GELU instead of the QuickGELU they were trained with, which it only warns about (`force_quick_gelu`). The last two change the game's own Atlas too (ViT-L/14 and ViT-B/32 OpenAI), so `EMBEDDING_VERSION` and `SALIENCY_VERSION` are bumped and the next Atlas run re-embeds and re-maps every photo. The Atlas run after it reached 0.86, still short: a fourth cause, transformers.js resizing through a canvas, which barely antialiases a full-size photo on the way down to 224 px. The browser now computes CLIP's input itself, a port of Pillow's bicubic resample and torchvision's crop (`web/src/lib/pocket/preprocess.ts`, pinned byte for byte to Pillow by `data/fixtures/clip_preprocess_cases.json`, whose reference is checked against open_clip's own transform); on the test images, including a 12-megapixel one, browser and open_clip then agree to cosine 1.0000
- [x] ML: Pocket Atlas's retrieval, scored: the reference photos (the same ones, past the same leakage guard) embedded by the browser's ViT-B/32 OpenAI model refine Pocket Atlas's own zero-shot guesses on the catalog photos, judged by the same paired bootstrap as the game's refinement; reported in `eval/results/atlas-v0.md` ("Pocket Atlas: would retrieval help the browser's model?") and written into `pocket-calibration.json` as `retrieval`, so the index can follow the verdict; the game's Atlas is never changed by it (`reembed_references` and `pocket_retrieval` in `run_atlas_v0.py`; the first result appears after the CI Atlas run)
- [x] ML + Web: Pocket Atlas's retrieval in the browser, if the verdict above says yes: `pocket-atlas-index` ships the reference photos' ViT-B/32 embeddings (int8) with their coordinates and place names only when `pocket-calibration.json`'s `retrieval.ships` is true, `locate()` in `pocket_index.py` and `locate.ts` move the pin to the weighted medoid of the 10 nearest references within the chosen country as `retrieval.py` does, pinned to each other by `data/fixtures/pocket_cases.json`, and the reveal names the reference photo the pin moved to with its credit; if the verdict is no, note it here and move on. **Verdict: no** (Atlas run of 2026-10-27: refined minus unrefined median +276 km, 95% CI -150 to +512 km on 388 photos), so nothing ships to the browser and Pocket Atlas keeps its zero-shot pin; the Atlas run keeps scoring it, and a later yes reopens this step
- [x] ML + Web: Pocket Atlas's clue heads: the driving-side and climate probes refitted on ViT-B/32 reference embeddings (`clue_heads.py`), shipped in the index and run in the browser, each replacing the zero-shot clue only where its paired accuracy gain is above zero (`pocket_clue_heads` in `run_atlas_v0.py` scores each probe on the browser model's own embeddings against what "Try Atlas on your photo" shows today: its zero-shot climate clue, and the driving side of the country it guessed; a winner's weights go into `pocket-calibration.json` as one affine map with standardisation folded in (`export_probe`), `pocket-atlas-index` carries every winner as `clueHeads`, and `locate()` in `pocket_index.py` and `locate.ts` take that group's clue from the probe ("Arid climate", "Drives on the left"), pinned to each other by `data/fixtures/pocket_cases.json`; "How Atlas works" and `eval/results/atlas-v0.md` report the comparison; the first result appears after the CI Atlas run)
- [x] ML: distillation, scored: a country head on the browser's ViT-B/32 embeddings of the reference photos, trained to match the playing ViT-L/14 Atlas's calibrated country distribution, scored on the catalog photos against today's zero-shot Pocket Atlas by the paired bootstrap (`ml/src/whereabout_ml/distill.py`, `pocket_distillation` in `run_atlas_v0.py`, docs/decisions/0008: a correction added to Pocket Atlas's own zero-shot logits / T, so the strongest penalty is today's Pocket Atlas; L2 chosen by held-out cross-entropy against the teacher over 10° geographic folds of the references; each game photo scored by a head that never saw its fold; ships only if the NLL interval is below zero, top-1 accuracy does not drop and the pin it leads to is not clearly further away; written to `pocket-calibration.json` as `distillation` and reported in `eval/results/atlas-v0.md`; the teacher embeds the references a chunk at a time under `--distill-budget-minutes`, so the first verdict appears once a CI Atlas run has them all)
- [x] ML + Web: the distilled head in the browser, if the verdict above says yes: `pocket-atlas-index` carries `distillation.head` (int8 or fp16), `locate()` in `pocket_index.py` and `locate.ts` add it to the tempered zero-shot logits for the "% sure", shortlist, heatmap and pin, pinned to each other by `data/fixtures/pocket_cases.json`, and the reality-check line uses the head's held-out `sureness` bands; if the verdict is no, note it here and move on. **Verdict: no** (Atlas run of 2026-10-28, the first with all 4,322 reference photos embedded by the teacher: held-out NLL -0.043, 95% CI -0.113 to +0.031 on 388 photos; top-1 accuracy +2.3 points, CI -1.0 to +5.9), so Pocket Atlas keeps its zero-shot countries. The browser side is built and tested on the `pocket-distilled-head` branch, ready for a later yes; the Atlas run keeps scoring it. The verdict only arrived because the Atlas workflow now queues another run while distillation's teacher still has reference photos to embed
